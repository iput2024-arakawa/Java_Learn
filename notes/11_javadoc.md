# トピック11: JavaDocによるドキュメント作成

## 1. これは何か、なぜ必要か

チームでコードを書くとき、「このメソッドは何をするのか」「どんな引数を渡せばよいのか」
「どんな例外を投げる可能性があるのか」を、コードを読まなくても分かるようにしておく
ことは非常に重要です。

**JavaDoc**は、Java標準の**ドキュメンテーションコメント**の書き方であり、専用のツール
（`javadoc`コマンド）を使うと、コメントからHTML形式のリファレンスドキュメントを
自動生成できます。また、多くのIDEはJavaDocコメントを読み取り、メソッド呼び出し時に
ツールチップとして説明を表示してくれます。

## 2. Javaでの書き方・構文（最小サンプル）

```java
/**
 * 従業員の基本給に基づいて、ボーナスを計算します。
 * ボーナスは基本給の20%として計算されます。
 *
 * @param baseSalary 従業員の基本給（0以上である必要があります）
 * @return 計算されたボーナス額
 * @throws IllegalArgumentException baseSalaryが負の値だった場合
 */
public int calculateBonus(int baseSalary) {
    if (baseSalary < 0) {
        throw new IllegalArgumentException("基本給は0以上である必要があります");
    }
    return (int) (baseSalary * 0.2);
}
```

ポイント：
- `/** ... */`（アスタリスクが2つ）で始まる特別なブロックコメントがJavaDocコメント
- `@param 引数名 説明` … 引数の説明
- `@return 説明` … 戻り値の説明
- `@throws 例外クラス 説明` … 発生しうる例外の説明
- クラス自体にも同じ形式でコメントを付けられます（「このクラスは何を表すか」）

## 3. Pythonとの対比

Pythonにも**docstring**（3連クォート`"""..."""`で囲むコメント）という、似た文化が
あります。

```python
def calculate_bonus(base_salary: int) -> int:
    """
    従業員の基本給に基づいて、ボーナスを計算する。

    Args:
        base_salary: 従業員の基本給（0以上である必要がある）

    Returns:
        計算されたボーナス額

    Raises:
        ValueError: base_salaryが負の値だった場合
    """
    if base_salary < 0:
        raise ValueError("基本給は0以上である必要があります")
    return int(base_salary * 0.2)
```

| 項目 | Python | Java |
|---|---|---|
| 書き方 | `"""..."""`（関数の中の最初の文） | `/** ... */`（メソッドの直前） |
| ツール | Sphinxなど（統一ルールは緩やか） | `javadoc`コマンド（言語標準で仕様が決まっている） |
| 引数の説明 | `Args:`セクション（ツールにより書式が異なる） | `@param`（Java言語仕様レベルで統一） |

大きな違いは、Javaの`@param`や`@throws`のようなタグは**言語仕様として決まっている**
ため、書き方に迷う余地が少なく、`javadoc`コマンドで機械的にHTML化できる点です。
Pythonのdocstringは書式に複数の流派（Google style、NumPy styleなど）があり、
使うツールによって解釈のされ方が変わります。

## 4. つまずきやすいポイント・よくある間違い

- **普通のコメント`//`と混同する**：`//`はJavaDocとして認識されません。
  必ず`/** ... */`（アスタリスク2つ）で始める必要があります
- **`public`なクラス・メソッドにだけ書けばいいと思ってしまう**：`protected`な
  メンバーも外部から見える可能性があるため、基本的にはドキュメントが必要です。
  一方、`private`なメソッドはJavaDocの対象外とされることが多いです（クラス外に
  公開されないため）
- **「何をしているか」をそのままコード的に書いてしまう**：`// nameを返す`のような
  コードの直訳ではなく、「なぜこのメソッドが必要か」「どんな制約があるか」を書くのが
  価値のあるドキュメントです
- **タグの記述漏れ**：`@throws`を書き忘れると、呼び出す側は「このメソッドが例外を
  投げる可能性がある」ことに気づけません。トピック7で学んだ例外処理と合わせて、
  丁寧に書く習慣をつけましょう
