# まとめノート：Java基礎〜オブジェクト指向（トピック1〜6）

これまで学んだルールを短くまとめたチートシートです。詳しい解説・理由は各トピックの
個別ノート（`01_basic_syntax.md`〜`06_abstract_interface.md`）を参照してください。
このノートは「思い出す」ためのもので、初めて読む用の解説ではありません。

---

## トピック1：基本文法

- Javaは**静的型付け**：`型名 変数名 = 値;` のように必ず型を書く（Pythonは型を書かなくてよい）
- 文末には`;`が必須
- 出力は`System.out.println(...)`
- プログラムは必ず`class`の中に書く。起点は`public static void main(String[] args)`
- `String`だけ大文字始まり（クラス型だから）。`int`/`double`/`boolean`は小文字
- コンパイル：`javac ファイル名.java`（または`javac *.java`で一括）
- 実行：`java クラス名`（拡張子なし。`public class`名と一致させる）

## トピック2：クラスとインスタンス

- クラス＝設計図、インスタンス＝実体
- インスタンス生成には**`new`が必須**（Pythonは`Dog(...)`だけでよい）
- コンストラクタ＝クラス名と同じ名前、戻り値の型を書かない特殊メソッド
- `this` ＝「このインスタンス自身」。引数名とフィールド名が同じとき区別に使う
  （Pythonの`self`は明示的に引数として書くが、Javaの`this`は暗黙的に使える）
- `public`なクラスは、ファイル名とクラス名を一致させる必要がある

## トピック3：カプセル化

- フィールドは基本`private`にし、`getXxx()`/`setXxx()`経由でアクセスさせる
- Pythonの`_score`は「触らないでねという申し合わせ」に過ぎないが、Javaの`private`は
  **コンパイラが強制**する（外部から書くとコンパイルエラー）
- setterにチェック処理を書けるのがメリット。**コンストラクタからもsetter経由で設定する**と
  一貫性が保てる
- `boolean`のgetterは`isXxx()`という名前にするのが慣習

## トピック4：継承（extends / super）

- `class Child extends Parent { }` で親クラスを継承（“is-a”の関係）
- `super(...)` ＝親のコンストラクタ呼び出し。**必ずコンストラクタの最初の1文**に書く
  （書き忘れると、親に引数なしコンストラクタがない場合コンパイルエラー）
- 継承できるのは`public`/`protected`のメンバーのみ。`private`は子クラスからも直接アクセス不可
- Javaは**単一継承のみ**（`extends`は1つだけ）。複数の型を扱いたい場合はインターフェースを使う
- 【発展】JDK 25/26以降は、自分自身のフィールドへの代入に限り`super(...)`より前に
  書けるようになった（Flexible Constructor Bodies）が、初学者のうちは
  「`super(...)`は必ず最初」で統一するのが無難（詳細は`04_inheritance.md`5節）

## トピック5：ポリモーフィズム

- 親と全く同じシグネチャ（名前・引数・戻り値）でメソッドを定義すると**オーバーライド**になる
- `@Override`は必須ではないが強く推奨（親に該当メソッドがなければタイプミスをコンパイルエラーで検出できる）
- **参照型（見た目の型）と実体（実際のインスタンス）は別物**
  - `Employee e = new Manager(...);` → `e`経由で呼べるのは`Employee`が持つメソッドの範囲だけ
  - 呼ばれる中身は実体（`Manager`）側の実装（動的束縛）
- フィールドはオーバーライドされない（ポリモーフィズムの対象はメソッドのみ）
- 「オーバーライド」（上書き）と「オーバーロード」（多重定義）は別概念、混同注意

## トピック6：抽象クラスとインターフェース

- `abstract class` は**直接`new`できない**。中身のない`abstract void メソッド();`
  （抽象メソッド）を1つでも持てば、継承した子クラスは**必ず全部オーバーライドしないと
  コンパイルエラー**
- `interface` は実装を持たない純粋な「契約」。メソッドは書かなくても自動的に`public abstract`
- クラスは`extends`（1つだけ）、インターフェースは`implements`（**複数同時にOK**）
- 継承関係が全くないクラス同士でも、同じインターフェースを実装していれば同じ型の配列にまとめられる
  （Pythonのダックタイピングに近いことを、静的型付けのまま実現する仕組み）
- 使い分けの目安：実装・フィールドを共有したい→抽象クラス／型の約束だけでよい→インターフェース

## Python対比・早見表

| 項目 | Python | Java |
|---|---|---|
| 型宣言 | 不要（動的型付け） | 必須（静的型付け） |
| インスタンス生成 | `Dog(...)`（`new`不要） | `new Dog(...)`（`new`必須） |
| 自分自身を指す | `self`（明示的な引数） | `this`（暗黙的） |
| アクセス制限 | 慣習（`_score`）、強制力なし | `private`をコンパイラが強制 |
| 親コンストラクタ呼び出し位置 | どこでもよい | 必ず最初の1文（新機能で一部緩和） |
| 多重継承 | 複数の親を継承できる | クラスは1つのみ、複数はinterfaceで |
| 「型」の約束のない共通処理 | ダックタイピングで自由に | interfaceで型として明示的に約束 |

## つまずきポイント総まとめ

- セミコロン忘れ、`new`忘れ、型の不一致 → 静的型付け特有の初歩的ミス
- `this.name = name;`の`this.`忘れ → 自己代入になり値が入らない
- コンストラクタで直接代入してsetterのチェックをすり抜けてしまう
- `super(...)`を最初の行以外に書く／書き忘れる
- 参照型（`Employee e = ...`）経由で呼べるのは、その型が持つメソッドだけ
- 抽象クラス・インターフェースを直接`new`しようとしてしまう
- 抽象メソッドの実装漏れ
